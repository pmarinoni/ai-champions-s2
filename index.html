The case — one decision, for everyone

Paste this into exercise 1 · fictional, for practice only

Unobravo is considering an AI assistant that prepares the therapist before each session. Before a call, it reads what the patient has written in the app that week and produces a 30-second summary for the therapist: mood trend, topics raised, anything the patient flagged as urgent. It never diagnoses, it never writes anything back to the patient, and the therapist can ignore it.

Proposed pilot: 40 volunteer therapists, 8 weeks, patients opt in explicitly and can switch it off at any time.

Ship it, kill it, or ship it with conditions?

Three ground rules, and they hold all session.
1 · Ask out loud. If a step feels unfamiliar, say so — someone else has the same question, and the answer is worth more to the whole room than to one person in a private chat.
2 · Write your own prompt first, then open the sample. Every exercise has one, closed by default — it's there for when you're stuck or want to compare, not to start from. They're also deliberately imperfect: if you spot an instruction that's missing, add it.
3 · A note on saving tokens, if you need to. Use Opus when you really need it, for the deeper reasoning, and Sonnet for the easier tasks. Set effort between Medium and High depending on how complex the task is. And every so often, click this icon to check your usage limits.
Before we start · 3 minutes
  1. Create a folder called unobravo-champions/ and mount it in Claude Code or Cowork: open a new session and select that folder; if one has already been selected, click on it and change it.
  2. Ask Claude to create a CLAUDE.md and a STATUS.md for this folder — plain language, no command needed:
    • "Create a CLAUDE.md for this project: it's my AI Champions practice folder, everything in it is invented practice material. Also create a STATUS.md, a running log of where the work stands."
    Then skim both files. STATUS.md is what tells you where you left off when you come back tomorrow — and in exercise 4 you'll add a hook that keeps it updated for you, without being asked.
01Subagents
20′

Evaluate a decision with five experts at once — then keep the panel

One agent can give you one opinion. Five subagents running in parallel give you five independent ones, each looking at the same decision through a different lens, none of them influenced by the others. Each one also has to land its verdict on a number — which key result this moves, which one it endangers — so the review comes back in the language the quarter is already written in. Then the interesting part: you save that panel to your project so the next decision takes one line instead of a whole prompt.

🎯 Goal A single review of the decision — five verdicts, the risks they agree on, which of this quarter's key results the decision moves and which it endangers, and one recommendation — plus five reusable subagent files sitting in your project folder, proven to work in a fresh chat.
📁 What you need
  • The decision text from the intro (copy button on the block above)
  • Your unobravo-champions/ folder, mounted
  • No connectors. Nothing leaves your machine in this exercise
Step by step
  1. Paste the decision into a new chat in your folder.
  2. Run the panel. It's one prompt, and it does three things.
    1. Ask for five subagents in parallel, one lens each — and be explicit that they must not see each other's answers:
      • clinical quality & safety · privacy and compliance · patient trust & brand · operations and support load · money and viability (describe them as you see fit)
    2. Define what each one returns — same five fields for all five, so the merge has something to line up: their verdict, their single biggest risk, the one condition that would make them say yes, what evidence would change their mind, and the key result this decision moves — and the one it puts at risk.
      • The fifth field is what turns a review into something leadership can act on. Give all five lenses the same key results — this quarter's OKRs (you can add your own). Examples (invented):
        • KR1 patient 3-month retention from 61% to 68%
        • KR2 zero privacy incidents, DPIA coverage at 100% of live features
        • KR3 patient NPS from 42 to 50
        • KR4 support tickets per 100 sessions from 9.4 to 6.0
        • KR5 contribution margin per session from 18% to 24%
    3. Let the main agent recompose — a lens-by-lens table, the risks that more than one lens raised, the OKR line (which key results this decision moves, which it endangers, and where two lenses disagree about that), and a recommendation (ship / kill / ship with conditions) with the three conditions that unlock it — and have it write the result to a Markdown file in your folder, e.g. decision-review-ai-summary.md.
      • Not just an answer in the chat: a file. Exercise 2 reads it, exercise 3's skill produces one every time, and a review that survives the chat is one you can send, diff and keep
  3. Now save the panel. Ask Claude to turn each of the five into a reusable subagent file inside this project — and to tell you where it saved them and why. Open one and read it: it's a Markdown file, exactly like a skill or a memory file.
  4. Prove the reuse. Open a fresh chat, paste the test decision below and ask for the same review from the saved panel — writing to its own .md, so the first one stays put. It's a completely different decision, not a variation: if the panel only works on the case it was born from, it isn't reusable. And if you had to re-explain the lenses, the save didn't work.

02/goal
15′

Turn the verdict into an HTML page that passes a bar

The review from exercise 1 is raw material. What you'd actually circulate is one page someone can read in a minute. So don't edit it by hand: write down what "good" means, once, as criteria a stranger could check — then let Claude grade its own work against them and keep fixing until it passes.

🎯 Goal A one-page HTML decision review you'd send to leadership, produced by a loop that stopped on its own — plus a change log showing what it fixed and why.
📁 What you need
  • The .md review from exercise 1 — point Claude at the file
  • The same chat you used for step 1
Step by step
  1. Decide what the page must contain before you write the prompt: the recommendation up top, the five lenses at a glance, the shared risks, the key results the decision moves or endangers, the conditions as a checklist.
  2. Write four or five criteria — every one checkable. A number, a time, a yes/no. "Readable in 60 seconds" works. "Compelling" does not — an unverifiable criterion just makes the loop guess.
  3. Add the three things that make this a goal loop — one that iterates towards a verifiable outcome and then stops on its own, not one that runs on a clock: a self-grade out of 10 each round, a change log, and a stop condition (9+ or five rounds, whichever comes first).
  4. Run it, then read the change log first — before the final page. That log is where you find out whether your criteria were any good.
Sample prompt
Prompt 
/goal Read decision-review-ai-summary.md in this folder and build it into a
single-page HTML artifact, then iterate it until it passes ALL of these:

· the recommendation is readable in the first 5 seconds, before any scrolling
· all 5 lenses are visible at a glance, each with its verdict color-coded
· every risk names who it lands on and which lenses raised it
· every condition is checkable — a number, a date, or a yes/no
· every key result named in the review appears with its direction: moved,
  at risk, or contested by two lenses
· the whole thing fits one screen at 1280px wide, no horizontal scroll
· nothing appears on the page that isn't in that file

Self-grade out of 10 each round, keep a short change log of what you changed and
why, and stop at 9+ or after 5 rounds — whichever comes first. Show me the change
log before the final version.
✅ Done when
03Skills
15′

Turn the whole chat into one command

Right now this chat contains a working process: five expert lenses, a recomposition, a page, and a quality bar. That's a skill you've already tested — you just haven't packaged it. Don't write a skill from a blank page; capture the one you just ran.

🎯 Goal /decision-review — takes any decision in one paragraph, runs the saved panel, and hands back the page that passes the same criteria.
📁 What you need
  • The chat from exercises 1 and 2 — capture happens inside it
  • The five saved subagents from exercise 1, so the skill reuses them instead of redefining them
  • A second decision to test on — one is provided in the sample prompt
Step by step
  1. Capture, in this chat: "turn this chat into a skill." The wording matters — you're asking it to write down what it just did, not to invent a process.
  2. Name it and define one input: a decision, in a paragraph. Nothing else.
  3. Point it at the saved panel from exercise 1 rather than letting it re-describe the five lenses. One source, not two that drift apart.
  4. Manual trigger only — it should never fire on its own.
  5. Now add it in the sidebar: Customize → Skills → Add → Upload skill. Until it's uploaded there, it's just a file in your folder — this is the step that makes /decision-review callable from Claude Chat, Cowork and Code, both locally and on the web, and shareable with your colleagues.
  6. Test it properly: new chat, different decision. "Unobravo replaces its written intake questionnaire with a 5-minute voice note the patient records in the app." If the output is worse than what you built by hand, the skill is missing something — fix it now, while you still remember what.
Sample prompt
Prompt 
Turn this chat into a skill called /decision-review.

Input: one decision, described in a paragraph.

It must reuse the five reviewer subagents already saved in this project — don't
redefine the lenses inside the skill, call the saved ones so there's only one
source of truth. Then it recomposes exactly as we did here (table, shared risks,
OKR line, recommendation with 3 conditions), writes that review to its own .md file in this
folder named after the decision, and builds the same single-page HTML artifact,
applying the same quality criteria before it hands anything back.

Manual trigger only — it must never activate on its own.

04Hooks
15′

Two hooks, one at each end of a turn

Every exchange has two moments a hook can grab: the instant before your message leaves, and the instant after the reply lands. A hook isn't Claude deciding to be careful — it's code that fires whether anyone remembers or not. Both of these are two lines of setup and thirty seconds to test.

🎯 Goal Two working, tested hooks, both scoped to this folder: a UserPromptSubmit hook that stops a message carrying someone's contact details before it's sent, and a Stop hook that appends a line to STATUS.md every time Claude finishes replying.
📁 What you need
  • Your folder, with the CLAUDE.md from setup
  • The STATUS.md you created at setup
  • A fake email address to test with — mario.rossi@example.com does the job
  • Nothing else — no connectors needed
Hook A · before your message leaves
  1. Ask for a UserPromptSubmit hook, this folder only, that reads your message before it's sent and blocks it if it contains an email address or a phone number — with a line telling you why.
  2. Tell it to add this hook leaving any other hooks untouched.
  3. Test it both ways, and don't skip the second half:
    • send "summarize the notes for mario.rossi@example.com" → it must stop you
    • send anything normal → it must go straight through

Contact details are what people actually paste by accident — a name and an email, pulled from a ticket without thinking. We could have written this in the CLAUDE.md file at setup, but a hook turns it into something deterministic.

Hook B · after Claude finishes
  1. Ask for a Stop hook — it fires the moment Claude finishes a reply — that appends one line to STATUS.md every time: what you asked, what it did, what's next.
  2. Tell it to add this hook leaving any other hooks untouched.
  3. Test it: ask something trivial, then open STATUS.md. It should have grown by a line you never asked for.
  4. If you finish early: ask once more and check it appended again rather than overwriting.

We could have written this in the CLAUDE.md file at setup, but a hook turns it into something deterministic.

Sample prompts
Hook A · UserPromptSubmit 
In this folder only, add a UserPromptSubmit hook that reads my message before it
is sent and blocks it if it contains an email address or a phone number.

When it blocks, show exactly this: "Send blocked — that looks like someone's
contact details. Everything in this folder is invented practice material. Take
them out and try again."

Add your own block only — don't modify any hook that's already configured.
Hook B · Stop 
Now, same folder only, add a Stop hook — the one that fires when you finish
replying — that appends one line to STATUS.md every single time: the date, what
I asked, what you did, and what's next. One line, appended, never overwriting
what's already there.

Add your own block only — don't modify any hook that's already configured.
✅ Done when
05Routines
20′

A cloud routine that briefs you every morning

Everything so far runs when you're there. This one doesn't: a cloud routine runs on Anthropic's side, on a schedule, with your laptop shut — which is also why it only sees what you've connected. Tomorrow at 8:00 you get a Slack DM that has already read your calendar, your unanswered mail and the threads waiting on you — including the dates people agreed to weeks ago and nobody has looked at since.

🎯 Goal A scheduled cloud routine that reads Calendar, Gmail and Slack, and DMs you one short morning brief: what's on today, what falls due in the next seven days, who's waiting on a reply, and what decisions are sitting with you. It reads everywhere and writes in exactly one place — a DM to you.
📁 What you need
  • The official Google connectors authorized (Calendar + Gmail)
  • The Slack connector authorized, so it can DM you
Step by step
  1. Write the brief you actually want before you touch Routines. Be specific about length and order — a morning brief that takes four minutes to read gets ignored by Thursday. Ask for: today's calendar, anything falling due this week, unanswered messages older than a day, and anything that looks like a decision waiting on you.
  2. Ask for deadlines by name, and make it count the days left. Not "upcoming", not "soon" — what is due, for whom, in how many days. Deadlines are the one thing a brief is genuinely better at than you are: they get agreed once, in a thread three weeks ago, and then nobody re-reads that thread.
    • Two rules worth writing into the prompt. Make it separate a date someone committed to from a date someone floated, and have it quote the line the date came from — otherwise you get a confident deadline nobody actually agreed on
    • If a deadline belongs to a key result — a check-in, a review, an end-of-quarter number — have it say which one. That's the same OKR thread from exercise 1, arriving on the day it matters instead of at the end of the quarter
    • Have it close the brief with any decision someone needs from you. Most will be small. When one isn't, that paragraph is exactly what /decision-review takes as input
    • Set the boundary explicitly: read-only everywhere, and the only thing it writes is the Slack DM to you. It must never reply to an email or post in a channel
  3. Run it once by hand, in a normal chat. Never schedule something you haven't seen work. Fix the shape here, where it's cheap.
  4. Now make it a routine: Claude Code → Routines → New routine → Cloud → paste the working prompt → schedule it for a weekday morning. Add the silence rule: if there's nothing worth saying, say nothing. A routine that pings you every day with "nothing to report" gets muted in a week, and then it's worse than not having it.
Sample prompt
Prompt · run it by hand first, then paste the same text into a Cloud routine 
Every weekday at 08:00, prepare my morning brief and send it to me as a Slack DM.

Read, using only the official connectors:
· Google Calendar — everything on my calendar today, with times, plus anything in
  the next 7 days that is a deadline, a review or a check-in
· Gmail — messages from the last 14 days that either wait on a reply from me or
  name a date, a due date or a commitment
· Slack — DMs and @-mentions from the last 24 hours I haven't answered, plus any
  message in the last 14 days where someone committed to a date

Then send me ONE DM, in this order, nothing else:
1. one opening line: the single thing today actually turns on
2. TODAY — my calendar as a list, time first, max one line each
3. DUE IN 7 DAYS — one line each, sorted by how little time is left: what, who
   it's for, how many days, and whether it's a date someone COMMITTED to or one
   someone FLOATED. If it belongs to a key result, name the KR. Quote the line
   the date came from. Omit the section if there's nothing due
4. WAITING ON YOU — max 5 items, each one line: who, what they need, how old it is
5. DECISIONS ON YOUR DESK — anything that reads like a choice someone needs from
   me, one line each, or omit this section entirely if there are none

Rules:
· Read-only everywhere. The ONLY thing you write is this DM to me. Never reply to
  an email, never post in a channel, never mark anything as read.
· Under 200 words total. If it doesn't fit, cut the least urgent item — never the
  deadline that's closest.
· Never invent or estimate a date. If nobody wrote one, say "no date agreed".
· If there is genuinely nothing worth telling me, send nothing at all.
· Never quote medical or clinical content from any message — say "clinical thread"
  and move on.
